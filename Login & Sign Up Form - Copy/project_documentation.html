1. Project Title, Purpose & Background Scope

The Secure Authentication & Access Management System (SAAMS) delivers an enterprise-grade identity governance, multi-factor credential authentication, and role-governed authorization framework. The system is engineered to secure modern cloud and on-premises enterprise portals against credential theft, lateral traversal, privilege escalation, and data loss.

Context & Codebase Origin: The presentation foundation originates from the project repository containing an interactive 3D flip-card client interface (index.html, style.css, and script.js). This document formalizes the production architecture binding that presentation tier to a hardened multi-tier backend, an on-premises transactional database, and an actively verified encrypted offsite disaster recovery infrastructure backed by Supabase Cloud.

2. Security Objectives & Threat Mitigation Model

Primary Security Objectives:

  • Confidentiality: Zero exposure of user plaintext credentials at rest, in transit, and during in-memory processing.
  • Integrity: Cryptographic verification of identity tokens, role authorization boundaries, and immutable audit logs.
  • Availability: Continuous operational resiliency via local low-latency ACID persistence backed by automated remote failover.

Threat Surface Mitigation:

  • OWASP Top 10: Immune to SQL injection via 100% prepared statements; CSRF protection via double-submit SameSite cookies.
  • Credential Attack Defense: Memory-hard Argon2id hashing plus isolated secret pepper eliminates offline GPU dictionary cracking.
  • Brute Force & Flooding: IP-adaptive rate limiting (maximum 5 attempts per 15-minute sliding window).

5. User Identification & Two-Factor Authentication (2FA) Architecture

Identity Governance: Each identity is assigned an immutable 128-bit RFC 4122 UUIDv4 primary key. Email addresses undergo strict RFC 5322 sanitization, lowercase normalization, and unique indexing. Passwords must satisfy NIST SP 800-63B standards (minimum 12 alphanumeric characters with special symbols).

Two-Factor Authentication (TOTP): Fully compliant with RFC 6238. Secret keys (160-bit Base32) are provisioned via QR code into standard authenticator applications (Google/Microsoft Authenticator). A 30-second time window with a ±1 step drift tolerance validates 6-digit codes. Upon 2FA enrollment, 8 single-use emergency recovery codes are generated and stored strictly in hashed format.

6. Multi-Tier Password Protection: Argon2id, Salt, and Secret Pepper

Passwords undergo a rigorous three-stage defense-in-depth cryptographic pipeline prior to persistent storage:

Cryptographic Execution Flow: Plaintext Password → Pre-Hash Pepper Injection (HMAC-SHA256(Password, Pepper)) → CSPRNG Salt Concatenation → Argon2id KDF → Output Hash String ($argon2id$v=19$m=65536,t=3,p=4$salt$hash).

CSPRNG Salt Generation: Every account generates a unique 16-byte (128-bit) cryptographically secure pseudo-random salt via crypto.randomBytes(16). This ensures distinct hash digests for identical passwords and defeats precomputed rainbow table attacks.

Isolated Secret Pepper: A 256-bit high-entropy secret key stored strictly outside the database (in environment variables or cloud Key Management Service / HSM). Even if the SQL database is compromised, password hashes cannot be computed without the external pepper.

7. Role-Based Access Control (RBAC) Permission Matrix

Authorization operates under the Principle of Least Privilege across four distinct organizational tiers:

Role Name Scope & Organizational Function Assigned Capabilities & Permissions Access Constraints
Inputer Data Operator / Clerical Entry Draft creation, credential submission, self-profile update, record entry. No approval or admin rights; read-only self scope.
Admin Operational Administrator User account provisioning, account unlocks, operational log review, record verification. Scoped to operational data; cannot alter system crypto keys.
Administrator System Superuser & CISO Delegate Full system governance, security policy enforcement, key rotation, RBAC assignment, audit purge. Dual-authorization required for master cryptographic reset.
Manager Departmental / Executive Supervisor Review workflows, approval/rejection of submitted records, aggregate reporting dashboards. No user credential management or security config access.
8. Local Database Operation & Secure Connection Protocol

Local Transactional Engine: Primary operations execute on an on-premises PostgreSQL instance configured in Write-Ahead Logging (WAL) archive mode. This guarantees sub-10ms transactional latency, ACID compliance, and complete data residency.

Secure Connection Security: Transport relies on TLS 1.3 socket encryption with sslmode=verify-full. All application queries utilize parameterized prepared statements, rendering SQL injection structurally impossible. Pooled connections enforce strict idle timeouts.

9. Automatic Encrypted Supabase Cloud Backup & Disaster Recovery

Disaster recovery is automated via backup_service.js executing snapshot streaming to Supabase (yzjalvfrgfvyjknpjrju.supabase.co):

Client-Side Envelope Encryption: Database dumps are encrypted locally prior to egress using AES-256-GCM. An ephemeral 256-bit Data Encryption Key (DEK) is wrapped by a Master Key (KEK). Payloads include a 96-bit IV, 128-bit auth tag, and SHA-256 plaintext integrity digest.

Live Supabase Drill & Point-In-Time Recovery: Encrypted payloads transmit over TLS 1.3 to Supabase bucket encrypted-backups. Recovery drill verification confirmed zero data corruption, exact SHA-256 integrity match, and Recovery Time Objective (RTO) < 2 seconds.
